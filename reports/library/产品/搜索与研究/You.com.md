## 一、摘要

- 一句话定位：**AI 原生搜索与助手**，强调可定制 Agent、多模式（如快速/深度类能力，以产品为准）与 **面向 LLM 的 Web Search API**，同时服务终端用户与开发者。
- 目标用户：希望「搜索即答案+来源」的消费者；需要 **实时、可引用网页结果** 的 AI 应用开发者。
- 核心工作流：输入查询 -> 选择模式与 Agent -> 查看摘要与链接 -> 可选继续多轮；开发者侧则通过 API 将检索结果注入自有模型或 Agent。

---

## 二、为何重要

You.com 处在 **「搜索产品」与「LLM 工具链」** 的交叉点：一边是 Perplexity 类答案引擎，一边是 **RAG/Agent 的基础设施供应商**。

**对 PM 的价值**：研究 **同一品牌下 ToC 与 ToB API** 的定价与能力切割；「零数据保留」等企业承诺如何写入产品卖点。

### 场景与痛点对照

| 用户场景 | 旧流程痛点 | 产品如何缓解 |
|----------|------------|--------------|
| 日常检索 | 蓝链海洋里自己拼答案；摘要站不可信 | 对话式答案+可点来源，减少无效点击 |
| 研究与写作 | 打开十几个标签做笔记，上下文难带回写作 | 多轮线程内追问与整理（视功能），降低窗口切换 |
| 开发者接实时网 | 自建爬虫合规与反爬成本高；结果结构不统一 | Web Search API 输出 LLM 友好片段，缩短 RAG/Agent 集成 |
| 企业检索治理 | 员工把敏感问题打到不可控消费级工具 | SSO、策略与（若承诺）数据保留控制，满足采购清单 |

## 四、核心工作流与交互模型

- **搜索 + 对话融合**：结果页与聊天线程结合，而非传统十条蓝链。
- **Agent 自定义**：用户或团队配置不同专长 Agent（与竞品 GPT/自定义助手类比）。
- **API 抽象**：把网页结果整理成 **LLM 友好格式**，降低集成门槛。

## 九、差异化与护城河

- 差异化：**消费者搜索 + 开发者 API 双轨**；企业合规叙事。
- 护城河：检索索引与工程、开发者集成广度；C 端品牌弱于 Google/Bing。
- 风险：默认搜索引擎入口被系统级产品占据；API 层竞争加剧。

---

## 十、商业模式与增长

- 消费者订阅 + 开发者按调用计费（以定价页为准）。
- 增长：API 进入更多 AI 应用默认栈；功能迭代与 ToC 口碑。

---

## 十一、风险、弱点与待验证

- 「AI 搜索」品类同质化，差异化需靠 Agent 与企业能力。
- 待验证：API 收入占比与 C 端粘性指标。

## 十二、PM 启示
### 12.1 PM 启示


- **同一检索内核** 可拆成 **两种产品形态**（终端 vs 管道）， KPI 完全不同。
- ToB 检索要卖 **合规、延迟 SLA、引用格式**，不是「和 Chat 一样好用」。
