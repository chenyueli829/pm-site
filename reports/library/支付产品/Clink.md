## 一、摘要

- **Clink 主产品**：面向 **SaaS 与全球化收款** 的 **订阅与计费 + 支付编排** 平台，官方叙事为 *Payment Infrastructure for an AI-Native World*。能力覆盖 **全球本地支付方式（宣传 100+）**、**用量计费（Usage-Based Pricing）**、**内置税务**、**智能路由与失败重试**、**订阅/账单/客户门户**、PCI 合规金库等。
- **Clink for Claw**：在 **OpenClaw /「Claw」生态** 中扮演 **Agent 运行时的资金与自动充值层**——当 Agent 执行中 **算力/商户余额不足** 时暂停任务，经 **Clink 嵌入支付与预算/风控** 完成 **自动 top-up**，再恢复执行；强调 **「Agent-ready」**、**低摩擦集成**（如通过 Agent Skills / SDK 声明「需要资金」）。
- **目标用户**：全球化 SaaS / AI 产品团队、需要 **订阅+多币种+本地支付** 的商户；以及 **托管 Agent 或 Token/积分型消费** 的平台方（与 Claw 路线结合时）。

---

## 二、为何重要

Agent 产品一旦 **按任务消耗算力或商户积分**，就会遇到经典断层：**支付发生在「人」的会话外**，而 **扣费发生在「Agent」运行时**。Clink for Claw 把问题表述为 **「任务中余额不足 → 暂停 → 充值 → 恢复」闭环**，属于 **Agent 经济基础设施** 的早期产品化样本。

**对 PM 的价值**：可对照 Stripe Billing、Paddle、Adyen 等，观察 **「通用计费」如何长出 Agent 专用叙事**；以及 **预算上限、日充值次数、风控拦截** 如何与 **自主执行** 并存。

## 三、目标用户与场景（含痛点）

### 3.1 主产品（Clink 通用）

### 场景与痛点对照

| 用户场景 | 旧流程痛点 | Clink 如何缓解 |
|----------|------------|----------------|
| 多国收款与结账 | 各地支付方式碎片化，自建网关集成与合规成本高 | 统一界面聚合网关与 **100+ 本地方式**（以官方为准） |
| 订阅与复杂计费 | 账期、升级降级、优惠券、税务各一套系统 | **Billing** 一体化：订阅、发票、客户门户、税务叙事 |
| 支付成功率 | 单一路由失败即丢单，跨境 decline 率高 | **Smart Routing**、动态路由与 **自动重试** 提升成功率和收入 |
| 用量计费 AI/SaaS | 纯订阅无法反映 token/调用量；对账难 | **Usage-Based Pricing** 与统一成本叙事，贴合 AI 产品 |
| 供应商锁定 | 迁移订阅与客户支付资料痛苦 | 宣传 **数据可迁移**、**Clink migration 端到端编排**（以合同为准） |

### 3.2 Clink for Claw（典型应用场景，重点）

以下基于官网 [Clink for Claw](https://www.clinkbill.com/clink-for-claw) 描述整理，便于 PM 做 **用户故事** 与 **风控设计** 对照。

| 典型场景 | 用户/系统行为 | 旧流程痛点 | Clink + Claw 如何缓解 |
|----------|----------------|------------|------------------------|
| **长任务跑到一半「没钱了」** | Agent 批量处理（如生成 100 张图到第 8 张）时 **Token/商户余额** 将不足以完成剩余工作 | 任务直接失败或卡死；用户事后才发现要充值，体验断层 | Claw **运行时自动做余额预测**；不足则 **暂停任务** 并拉起 Clink 流程，目标为 **整环在约 60 秒内**（官网叙事） |
| **用户首次绑定支付方式** | 暂停界面提示「需绑定支付方式才能自动充值」 | 用户不知道去哪付钱、怕乱扣款 | **嵌入式安全支付界面**，绑定卡/Apple Pay/PayPal 等（页面展示多种方式） |
| **自动充值（无人值守）** | 用户授权后，余额触及阈值 | 每次手动充值打断 Agent「自主」心智 | **Smart automatic top-up**：授权后 **接近临界值自动扣款**，减少 **零延迟执行** 上的人为干预（官网 copy） |
| **预算与风控（防 Agent 刷爆卡）** | 自主扣款引发「会不会一直扣」焦虑 | 纯自动充值无上限时用户不敢开 | **每日预算上限**、**单日最大充值次数**、**异常交易暂停** 等 **Merchant 级护栏**；页面示例含「Daily Recharge Limit Reached」类拦截 |
| **推荐充值金额** | 用户不知道充多少够跑完当前任务 | 充少再断、充多占资金 | **Smart Top-up Analysis**：展示 **剩余任务估算成本**、**建议充值额**、**充值后余额**（官网流程 demo） |
| **全球化 Claw 用户付款** | 不同国家卡与本地习惯不同 | 只接单一卡组织丢转化 | 宣传 **135+ 货币** 与 **100+ 本地支付方式**，与 Claw 扩张市场同步（同页） |
| **开发者接入 Agent** | 每个产品自建支付暂停/恢复状态机 | 重复造轮子、PCI 与合规重 | 叙事为 **「一行/Skill 级集成」**：Agent 声明需要资金，由 Clink 处理；页面引用 **Agentic Payment Skill**（GitHub：`modelmaxio/skills`，以仓库为准） |

### 3.3 场景一句话归纳（关注点速记）

- **Clink for Claw 的典型应用** = **「可消费的 Agent 运行时」**：在 **按量扣商户积分/算力** 的产品里，把 **支付、充值、限额、风控** 嵌进 **任务暂停/恢复循环**，使 **长时间自主任务** 在商业上可持续。

## 四、核心工作流与交互模型（Claw 专项）

1. **检测**：Agent 执行中预测 **当前余额是否覆盖剩余目标成本** → 不足则 **暂停** 并暴露状态（示例：*Token balance too low · task paused*）。
2. **拉支付**：唤起 **Clink 嵌入 UI** → 绑卡/选支付方式 → 可选配置 **Agent spending limits**。
3. **授权自动充值**：用户同意后 → 余额到阈值 **自动 top-up**。
4. **风控层**：实时风险评分 + **每日充值上限、频次上限、异常暂停** 等规则；命中则 **阻断自动充值** 并让用户 **改规则或手动充值**（示例 UI：*Risk Rule Met · Auto-Top-Up Blocked*）。

## 五、关键技术分析

- **通用 Clink**：支付编排 + 订阅生命周期 + 税务 + 门户 → **「Scale Global, Bill Local」**。
- **Clink for Claw**：在通用能力上叠 **Agent 触发式充值、嵌入式收银台、预算/频次/异常规则** → **「Agent-Ready Billing Layer」**。

## 六、首次使用与重复使用

- **主产品**：商户首次为 **跨境+订阅** 一站式接入；复用为 **对账、路由优化、客诉减少**。
- **Claw 线**：用户首次在 **任务中断时** 完成绑卡与限额；复访为 **静默自动充值** 与 **规则调整**。

## 七、差异化、护城河与风险

- **差异化**：**Agent 场景下「暂停—充值—恢复」闭环的产品叙事** + 与 **Claw 生态** 的联合页面与 Skill 集成；通用侧与 Stripe/Paddle 等在同一红海。
- **护城河**：**早期与 Claw/OpenClaw 分发绑定**、路由数据与成功率优化、合规与区域覆盖深度；**长期** 仍受 **品牌信任、牌照与资金渠道** 约束。
- **风险**：**「Agent 自动扣款」** 的监管与用户信任；**Claw 生态体量与命名分散**（OpenClaw、多托管商）导致 **集成碎片化**；宣传口径（如 *10 Million Claws*）需以实际渗透 **to verify**。

## 九、产品介绍（5W+ 简版）

| 要素 | Clink 通用 | Clink for Claw |
|------|------------|----------------|
| **What** | 全球支付 + 订阅计费 + 路由/重试/税务 | 上述能力 + **Agent 运行时充值与风控** |
| **Why** | 跨境与订阅复杂度高、成功率与合规贵 | Agent **中途断粮** 无法商业化闭环 |
| **How** | API + Hosted Checkout + 控制台 | 嵌入式支付 + 自动 top-up + 预算/频次规则 |
| **Who** | 全球化 SaaS / AI 商户 | **Claw/OpenClaw 用户与托管算力/积分的平台** |
| **Where** | 全球支付 TAM；红海 | 依赖 **Agent 消费形态** 渗透，属增量市场 **to verify** |
| **Competition** | Stripe、Adyen、Paddle、本地 acquirer 组合 | **通用计费竞品** + **自建钱包/预充值** 间接替代 |
| **Moat** | 路由数据、区域方法覆盖、迁移服务叙事 | **与 Claw 官方/社区集成深度**、Agent UX 标准 |
| **Technology** | 编排、PCI、风控工程 | **状态机与 Agent 运行时对接**、非单点模型算法 |

## 十二、PM 启示

- **Agent 商业化的关键中间层** 不是「能聊天」，而是 **可中断、可充值、可限额的资金流**。
- **自动扣款** 必须配 **可理解的暂停原因 + 用户可控上限**，否则转化与客诉双崩。
- **「Pay with Agents is coming」** 类叙事预示 **计费层与 Agent 入口绑定** 的渠道竞争，PM 需关注 **谁成为默认钱包**。
